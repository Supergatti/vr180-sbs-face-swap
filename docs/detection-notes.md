# 2026-06-27 SBS-YOLO 思路讨论

## 早期方案记录（2026-10-10）

> 本节及下方“原始想法”和路线 A/B/C 保留为探索记录。最新执行规划以 [VR180 SBS 人脸处理实施计划](VR180-SBS-人脸处理实施计划.md) 为准，该计划按需求重新设计。

### 目标与原则

- 先解决“尽量不漏脸”，输出用于人工监控、导出和后续处理的粗框；暂不把自研球面检测模型作为近期前提。
- 保留 PNG 监控导出，并为每批结果保存检测框/状态等结构化记录，便于发现漏检、重复框和坐标错误。
- 完整扫描模式必须覆盖所有预设观察方向。肤色等廉价线索可以用于排序，但不能作为跳过某方向的硬门槛；跳帧/跟踪只作为之后的可选加速模式。

### 近期主路线：保留多视角检测，先消除重复推理开销

使用现有透视探测视角和人脸检测器，先把每帧的 14 个探测视图组成一个 batch，一次送入 ONNX Runtime，而不是逐个视图分别调用模型。这样保留多视角对边缘畸变、近处人脸和偏转人脸的覆盖，同时减少重复的推理调用与数据搬运。

1. 保持当前全量探测视角和高召回阈值；继续输出 PNG 监控图及 JSON 检测结果。
2. 将 14 个视图统一缩放/填充到相同输入尺寸，堆叠成 `[N, 3, H, W]` batch；对齐输出索引与各视图的球面坐标变换，再合并重复框。
3. 检查当前 ONNX 模型是否支持 batch 大于 1。若模型固定为 batch=1，重新导出支持动态 batch 或固定 batch=14 的 ONNX；先用 CUDA Execution Provider，之后再比较 TensorRT Execution Provider（含 FP16 和 engine cache）。
4. 先用小批量视频做准确性和耗时对照，确认所有视图均被处理且框映射正确，再扩大到整段视频。

本机已有的一次性能尝试中，CPU `cv2.remap` 生成 14 个小视图约为数毫秒；逐视图调用 Torch GPU 重映射反而约数百毫秒，而批量 `grid_sample` 约数毫秒。该结果只说明“不要逐张把小 remap 搬到 GPU”，不能视为不同机器或完整流水线的性能承诺。近期先保留 CPU remap，把工程重点放在检测器 batch 化；不要把 14 次 remap 直接改成 14 次 GPU 调用。

### 后续优化阶梯

1. **先做检测 batch 化**：风险较低，通常不改检测器语义，是当前首选。
2. **再做融合 GPU 几何路径**：只有 batch 化后 remap 或主机/显卡间传输仍占显著时间，才尝试把 ERP 帧上传一次，在 GPU 上批量生成所有透视视图，并用 ONNX Runtime I/O Binding 传递 GPU 张量，避免每个视图单独上传/下载。
3. **最后评估时序跳帧**：仅作为可选快速预览。默认全扫描不跳帧，以免新进入画面的脸在检测间隔内漏掉。
4. **长线再训练 ERP/球面定位器**：积累有代表性的人工校正样本后，考虑畸变感知增强和球面坐标输出；它是后续研究项，不阻塞当前可用性。

### 双目与导出约束

- 继续优先使用右眼现有 NCC 立体匹配；匹配不可靠或失败时用检测器兜底，不能因匹配失败而丢弃已检测到的人脸。
- PNG 是必需的监控产物，不以关闭 PNG 作为默认提速手段。后续可单独测量导出耗时，再提供“全部导出/抽样导出”设置；默认行为保持可观察。
- 一次任务应保存可追溯的进度与检测记录，至少包含帧号、视角、框、置信度和处理状态；中断后能识别已完成与待处理部分，避免盲目重跑。

### 验收方式

用人工标注的小型代表性样本集对比改动前后：覆盖画面中心、左右/上下边缘、近脸、小脸、遮挡和多人场景。主要指标是人脸召回率及漏检样例，其次记录每帧误检数、单帧稳态耗时和 P95 耗时。先确认召回率没有回退，再判断是否达到速度收益；不以单一置信度阈值或平均 FPS 代替漏检检查。

## 原始想法

> 使用 transformers 位置编码，让模型学会人脸特征与位置的关系，直接跳过导出透视再识别这一步。训练的时候用 YOLO 的人脸识别为基准，也许能训练出一个 sbsyolo？

## 核心想法澄清

**目标**：轻量化模型直接在 ERP/SBS 球面图像上给出人脸大概位置 (θ, φ)，省掉 "球面→透视→拼接→YuNet→逆映射" 这一步。

**完整管道三阶段**：
1. ① 轻量球面定位器（**缺失，需要做**）→ 输出 (θ, φ) + 粗略框
2. ② facefusion 自带 YOLO + 换脸链路（**已有**）
3. ③ 反变换融合回 ERP（**已有**）

① 不需要精准，只需要不丢脸。后面的 facefusion 链路负责精细活。

### 技术路径：三段式管道

```
┌─────────────────────────────────────────────────────────────┐
│ 完整管道                                                     │
│                                                             │
│  SBS ERP 帧                                                  │
│      │                                                      │
│  ┌───▼──────────────┐    ┌──────────────┐    ┌────────────┐ │
│  │ ① 轻量球面定位器  │───▶│ ② facefusion  │───▶│ ③ 反变换   │ │
│  │  (缺失，需要做)   │    │   透视换脸    │    │   ERP 融合 │ │
│  │                  │    │  (已有)       │    │  (已有)    │ │
│  │ 输入: ERP 整帧   │    │              │    │           │ │
│  │ 输出: (θ,φ) 列表 │    │ 输入: 透视脸  │    │ 输入: 透视 │ │
│  │      + 粗略框    │    │ 输出: 换后脸  │    │ 输出: ERP  │ │
│  └──────────────────┘    └──────────────┘    └────────────┘ │
│                                                             │
│  关键：① 只做粗略定位，跳过 remap 探测，一步到位              │
└─────────────────────────────────────────────────────────────┘
```

**① 的定位：到底要多"轻"？**

当前管道开销分布：
```
remap 3张透视拼图:     ~6-10 ms  ← 球面→透视的几何计算
YuNet ×3 tile 检测:   ~3-8 ms   ← 检测本身
球面逆映射 + NMS:      ~1-2 ms
立体匹配 (NCC/YuNet):  ~5-15 ms
透视导出 remap:        ~3-5 ms   ← 高清透视切片
─────────────────────────────────
总计:                  ~18-40 ms/帧
```

目标是把前三行（~10-20ms）替换成一步 ERP 直接推理。轻量模型的推理时间需要控制在 **5-10ms 以内**才有意义。

### 三条可选路线（从易到难）

|     | 路线 | 改动量 | 风险 |
|-----|------|--------|------|
| A   | 直接在 ERP 图上跑 YuNet + 球面坐标解码 | 最小 | 两极畸变区域可能漏检 |
| B   | YuNet/YOLO-nano + 球面位置编码通道 | 小 | 需要构造训练数据 |
| C   | 从头训练专用的 "ERPLocator" | 大 | 数据量、训练时间 |

**路线 A（零训练，最值得先试）**：YuNet 本身是尺度、位置不变的——理论上如果直接把 ERP 图喂给它，也能找到"人脸状"的东西。不是要精准检测，只需要大概位置。畸变严重的区域（φ 接近 ±π/2），人脸本来就很少出现（VR180 视频中，人脸通常在 φ ∈ [-40°, +40°] 范围内）。

**路线 B（你的原始思路）**：给轻量模型的输入层拼接球面位置编码通道，用现有管道输出作为训练数据（自举训练）。

**路线 C（兜底方案）**：设计 2-3 层极简网络，输入下采样到 160×320，只回归 (θ, φ) + 置信度。回归式检测（类似 CenterNet），比 YOLO 更轻但调参成本更高。

## 技术启发

### 1. 现有开源零件（无完整方案，但有零件可组装）

| 零件 | 仓库 | 说明 |
|------|------|------|
| SphereNet | ChiWeiHsiao/SphereNet-pytorch (⭐130) | 球面卷积，改 kernel 采样位置 |
| CoordConv 官方 | uber-research/CoordConv (⭐210) | 仅 TF，加 (x,y) 坐标通道，已归档 |
| CoordConv PyTorch | mkocabas/CoordConv-pytorch (⭐396) | PyTorch 版 CoordConv |
| YOLO+CoordConv | 阿里云/腾讯云中文教程 | 已有 YOLOv5/v8 + CoordConv 嵌入代码 |

**关键结论**：有零件，没整机。"sbsyolo" 是 CoordConv + YOLO + 球面坐标 (θ,φ) + ERP 训练数据的组合，这个组合目前还没有人公开做过。

### 2. 球面位置编码 (Spherical PE)

CoordConv 用的是笛卡尔 (x,y) 坐标，需要替换为球面角坐标：

```
theta = (u / erp_w - 0.5) * pi          # [-π/2, π/2] 左右
phi   = -(v / erp_h - 0.5) * pi         # [-π/2, π/2] 上下
```

多频 sin/cos 编码作为额外输入通道 (RGB 3ch → RGB+PE 6-9ch)，让模型感知每个像素在球面上的绝对位置。改动极小，只在 YOLO 输入层拼接几个通道。

### 3. YuNet vs YOLO 性能认知

| 指标 | YuNet (OpenCV) | YOLOv8 nano |
|------|---------------|-------------|
| 参数量 | ~85K | ~3.2M |
| 模型大小 | 337 KB | ~6.2 MB |
| CPU 单帧 | ~8-15 ms | ~40-80 ms |
| GPU 单帧 | ~3-6 ms | ~5-10 ms |

**YuNet GPU 加速不显著的原因**：
- 模型太小（85K 参数），GPU kernel 启动 + 数据传输开销 > 计算本身
- 深度可分离卷积 arithmetic intensity 低，GPU 显存带宽成为瓶颈
- OpenCV DNN CUDA 后端不做 kernel fusion，不用 Tensor Core
- GPU 上的 YOLO 和 YuNet 差距只有 1.5-2x

**真正省时间的不是换检测器，而是跳过 remap（球面→透视 3 次重映射）**。

### 4. 数据量估算

| 策略 | 最少数据量 | 说明 |
|------|-----------|------|
| 零训练（直接 ERP 跑 YuNet） | 0 | 先做实验，看召回率能否接受 |
| 微调 YOLO-nano + PE | 5K-10K 帧 | 冻结 backbone 早期层 |
| 从头训练轻量定位器 | 30K-50K 帧 | 需覆盖足够 ERP 位置 × 人脸外观 |

**数据来源**：用现有 main.py 管道跑 50-100 个 VR180 视频，每帧产出 `spherical_faces.json` 作为伪标签（自举训练）。

### 5. 相关论文

- **SphereNet** (ECCV 2018)：球面卷积，数学严格但推理慢。PyTorch 实现可用但久未维护
- **CoordConv** (NeurIPS 2018)：坐标卷积，证明位置感知对检测有帮助。核心思想：CNN 的平移不变性在需要空间感知的任务上是劣势
- **YOLOv8 + ERP Augmentation** (2025)：印度尼西亚研究者在 360° 视频上用 ERP 特定数据增强训练 YOLOv8，mAP50 0.68→0.71。纯数据层面，无模型改动
- **STRING** (ICML 2025)：Lie 群位置编码泛化到任意维度，技术前沿
- **EDM** (CVPR 2025)：ERP 特化的稠密特征匹配
